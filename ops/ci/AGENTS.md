# NewsHub CI Rules

Read [root rules](../../AGENTS.md). These rules also apply to `.github/**`, root Agent rules and `.agents/**`, even when the file is outside `ops/ci/`.

- Workflow triggers and Job conditions live in `.github/workflows/ci.yml`; `change_scope.py` owns path classification. Read [routing guide](change-routing.md), then inspect actual code. Do not duplicate classification tables in Skills or weaken docs-only/unknown-path behavior.
- Keep the existing frontend listener without DinD access, backend private socket/volumes and trusted **same-repo** policy. Draft PRs only run quick scoped checks; Ready PRs and main/manual runs use the complete merge gate. No production secrets, host Docker socket, global prune or service restart while a job is busy.
- Keep `benchmark-xdist.sh`'s serial-sensitive modules and limited parallel remainder, dynamic collected/executed identity reconciliation and JUnit checks. Test counts and approved skips belong to the existing audit implementation, not Agent files.
- Before pushing, opening/promoting a PR or dispatching full checks, apply the root user-acceptance gate. Keep development local with necessary targeted checks until the user confirms the feature is ready for push/testing; a Draft push still triggers CI and is not an exception.
- For authorized new feature PRs use Draft during iterative development; never run full pytest, all Vitest, provider protocol tests, production image, or G1 on every Draft push. Promote Ready only after user acceptance plus review/targeted tests; returning to development means converting back to Draft before further pushes. Route ordinary frontend/backend changes as before. Agent/CI root changes require both stacks; child rules follow their existing path. Run the dependency-free `agent_rules.py` in frontend fast preflight and existing backend unittest discovery so a frontend-only rule edit cannot miss validation.
- Update classifier tests, CI contracts, release-operation workflow contracts and the routing guide together only when the routing contract actually changes. Do not change CI for ordinary feature development.
- Keep manual `workflow_dispatch` as full verification. A skipped/missing job is not PASS; distinguish intentional path suppression from detection/Runner failure. A failure in the changes job cannot be reported as successful routing fallback.
- Read the [build/release policy](build-release-policy.md) before changing build inputs, dependencies, caches or Runner settings. Declare expected invalidation; preserve unchanged install commands/cache IDs. Keep dependency layers before source COPY and release metadata late. Maintain the existing build regressions.
- Report layer hits separately from download hits; preserve failures and classify their causes before a bounded rerun. Compare matching SHA/digest/workload/cache conditions; never treat skipped gates or cold-versus-warm differences as speedup. Offline tests and authorized networked builds need different client setup.
- For review, require the non-Draft `merge-gate` and selected full jobs to succeed for the exact candidate and current base. Base changes require revalidation. Draft checks, old green runs and GitHub mergeability do not authorize merging; apply this even without branch protection.
- Validate Agent files with `python3 ops/ci/agent_rules.py`; regressions: `python3 -m unittest discover -s ops/ci/tests -p 'test_agent_rules.py'`. New owned rules/Skills must be registered and covered by negative tests. These checks are structural, not proof of model compliance or token savings.

## Code Review Rules
Flag loss of coverage, unsafe skip rules, untrusted Runner execution, leaked secrets or weakened gate semantics. Reuse the existing Actions workflow and dependencies rather than adding a separate Agent CI service.
