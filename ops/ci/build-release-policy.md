# CI 构建与发布合同

本文件是构建输入、缓存失效、故障分类和发布证据的统一操作规则，由根、CI、部署及测试 AGENTS 引用。它不授予推送、完整测试、镜像构建、G1 或生产操作权限；授权仍以[根规则](../../AGENTS.md)和当前用户指令为准。实际触发条件只由 [CI workflow](../../.github/workflows/ci.yml) 与 [change_scope.py](change_scope.py) 决定，[分流说明](change-routing.md)解释开发／合并阶段。不要在其他文档复制第二套路由表。

## 1. 为什么开发中会逐渐变慢或失败

| 来源 | 已有证据／边界 | 必须采取的处理 |
|---|---|---|
| 安装命令、cache mount ID、基础层改变 | [历史 #1036](https://github.com/CoderLambert/news-aggregator/actions/runs/40220008704) 中 Torch 重建 33.6s、后端依赖 63.1s；新增下载缓存也会改变 RUN 的缓存键 | 记录变更及预期一次性失效；不要将首次构建与旧版热缓存作性能 A/B |
| 非运行时文件参与应用 COPY | 本地仅增加两个测试文件，旧版重跑 COPY/Vite；收窄上下文后保留命中 | 测试、文档、工作树不进入应用构建输入；CI checkout 中的测试仍执行 |
| 浮动基础镜像／解析环境变化 | 浮动 tag 存在上游漂移风险；本次对比实际解析的 digest 相同，不是此次 104s 增量的原因 | 使用受审查的 digest；显式升级并验收，不为缓存命中永久冻结安全更新 |
| 发布 SHA 过早进入构建层 | SHA 改变会影响其后 RUN 的缓存键 | SHA 仅用于后置校验和标签，不作为依赖安装、用户/目录初始化的输入 |
| 混用不同层次缓存 | pip `Using cached` 仍会解析、安装；BuildKit `CACHED` 才表示整层复用 | 分开报告下载、已安装环境、镜像层，不能只写“缓存命中” |
| 业务缺陷、验收环境错误 | T06 shutdown 竞态有确定性回归；另一次验收 client 的 `--network none` 阻断 Docker Hub auth | 分别修业务或测试环境；不得用清缓存、重复运行或放宽断言掩盖 |
| 只看总时间或旧成功记录 | 完整测试、镜像、G1 未执行的失败运行更短；历史构建未必对应当前 SHA | 绑定 SHA、实际执行范围、退出码、缓存状态，成功与失败分开统计 |
| 测试和依赖规模随开发增长 | 不同提交的工作量可能不同，耗时增加不能全部归因于缓存 | 记录实际测试身份/数量及慢用例；按关键路径优化，不靠删测试、减少对账或增大并发掩盖 |

这些机制可以降低重复问题的概率，不能保证任何依赖升级、网络波动或业务修改都不再失败。

## 2. 修改前：先声明输入和预期失效范围

每次涉及构建、缓存、依赖或 Runner 的任务，先确认分支、base/head、完整 dirty 状态，并用以下五项写一个简短说明；普通业务改动无须另写长计划。

1. 改动类别：业务源码／测试或文档／依赖／基础镜像或工具链／构建层或 cache ID／Runner 配置。
2. 输入指纹：受影响的 lock、安装命令、cache ID、Python/Node ABI、架构、镜像 digest；未变化的输入明确复用。
3. 预期失效：哪一层应重建、哪一层应保持命中；是否存在一次性预热成本。
4. 验证范围：已有契约、负例、是否需要获准的真实构建；不能拿 mock 代替真实 BuildKit/G1。
5. 回滚：代码提交／镜像 ID／数据或迁移分别如何处理；不以清空共享缓存作为回滚。

不得为普通功能顺手改版本、安装参数、cache ID、Runner 镜像、CPU/内存限额或测试分流。必要变更必须给出原因、消费者和定向证据。

## 3. 构建输入和缓存不变量

- 根 Dockerfile 的 syntax frontend 和外部 FROM 固定 digest，保留所需版本及架构。升级必须显式修改并核对实际解析 digest。CI Runner、G1、RSS 各有自己的 Dockerfile/依赖合同，不把根镜像检查通过扩大成全部基础设施都已锁定。
- 先复制依赖清单、安装依赖，再复制应用源码。禁止把 `COPY .`、测试/文档、发布 SHA、时间戳、运行号放进昂贵依赖层的前置输入。前端也必须先 lockfile/npm 安装，再复制前端源码。
- 保留 Torch 与普通 Python 依赖的层次、现有 cache mount ID 和 `sharing=locked`；安装器与消费者遵守既有共享/排他锁。改 cache ID/安装命令就是缓存迁移，须说明失效与重用范围；不得仅为“刷新”随机生成 key。
- `.dockerignore` 必须排除 `.worktrees/`、Agent 产物、已确认的非运行时测试/文档、数据库、凭据、宿主 venv/node_modules。迁移、模板、静态文件、必要夹具和实际运行代码必须保留。新 COPY 或 ignore 否定规则要先检查消费者并同步契约，不能通过笼统排除所有 fixtures 来减小镜像。
- 精确的 `RELEASE_SHA` 校验及 revision label 位于可复用初始化之后；生产保持非 root，默认开发 target 保持原兼容语义。不得缓存整个“CI 成功”，或因为已有镜像而跳过测试、实际构建命令、镜像身份校验和选中的 G1。
- 使用 CI Python 3.12 / Node 22 与既有 `install-*-deps.sh` 环境；先检查已有环境匹配性，不在每个 worktree 重新安装。不得把 CI 的 lock 当作生产 lock：当前 `backend/requirements.txt` 含范围依赖，生产冷构建仍可能解析不同的传递版本。真正的生产锁定属于独立依赖变更，需专门验证，不能仅凭 pin 基础镜像宣称完全可复现。
- 没有已证明损坏，不执行 refresh/reinstall；有损坏时只处理对应指纹，先保留诊断。GC 使用现有 `manage.sh cache-gc` 预览／受授权执行入口；禁止全局 prune、清卷或重启忙碌 Runner。

## 4. 网络与资源：离线测试和真实构建分开

- mock／静态测试使用无网、只读源码与兼容依赖缓存、合成 HOME/数据库。真实生产构建只有获准后执行；Docker client 和 builder 可能都需要 registry/auth/package 网络，不能无条件沿用 `--network none`。
- 本地镜像验收使用独立 client 与现有 CI 私有 DinD socket／网络；先只读检查 Runner busy、本地 Worker 和背景负载。不得连接宿主 Docker socket构建、进入服务 Runner 执行测试、暂停别人的任务或重配网络来加速。
- 网络预检只输出状态，不输出匿名 token 或凭据。失败先区分 DNS、路由、TLS、认证和依赖错误，禁止关闭 TLS 校验或把秘密写入 Dockerfile/build args。
- 所有可写 context、容器、tag、端口和报告使用任务唯一名；从文件名层面排除 DB/凭据后才复制源码。worktree 不隔离 Docker、卷或缓存。清理只触及本任务资源，报告保留的镜像与临时目录。

## 5. 验收、指标与失败处理

### 开发中的必要检查

使用现有测试框架，按语义选择范围；当前 Agent 可直接验收，或按需委派：

```bash
python3 ops/ci/agent_rules.py
python3 -m unittest discover -s ops/ci/tests -p 'test_agent_rules.py'
python3 -m unittest discover -s ops/ci/tests -p 'test_image_build.py'
# CI / 发布合同变更再选相应已有测试；并非每次文档修改都要跑全套。
```

规则/链接与构建合同的自动检查接入已有 CI 入口，不新增并行的 CI 系统。自动检查只证明所覆盖的不变量；不证明 Agent 一定遵守规则，也不证明性能提高。

### 获准后的真实构建验收

CI 始终用 [build-production.py](build-production.py) 包装原生产 target 命令，输出实时 BuildKit plain log、JSON 和 Step Summary。保留真实退出码和取消信号，不重试失败构建。独立实验如需唯一标签可直接使用同一 production build 参数，但须说明与 wrapper 的区别。

构建/缓存变更的实测最少覆盖：首次采用新输入（单独记录）、同输入交替重复、只改测试文件、改应用源码。依赖或基础镜像本身发生变化时，另外验证预期失效；不得为实验全局清缓存制造“冷启动”。记录 n、median/range、base/head、实际 digest、资源/背景负载、完整命令、exit、每层执行/CACHED、context transfer 和实际执行的门禁。

- 总构建时间用 wall time；并行层耗时不能直接相加。
- 纯源码／测试变动且依赖输入相同时，依赖层预期命中；测试变化不应重跑应用 COPY/Vite。出现违背预期的 miss，先查指纹/层父链/缓存是否存在，不先改性能结论。
- 首次初始化、稳定热缓存、源码变化、依赖变化、排队时间分别统计。小样本只作为有限证据；不将局部收益外推为整体 CI 提速。
- 失败运行、跳过门禁、环境错误不算性能通过。完整 CI 的每阶段都要有完成状态；不比较“完整成功 10 分钟”与“提前失败 3 分钟”来宣称优化。

任何失败先保留原始日志、SHA、环境和退出码，再分类：源码缺陷补确定性回归；环境缺陷核实可复现原因；网络故障检查实际网络边界；缓存损坏要求具体证据。只在原因和修正明确后执行新的、有界验证组，保留失败尝试，禁止 retry-until-green。未知原因保持 UNKNOWN/BLOCKED，不能猜成环境问题。

## 6. 从本地开发到部署

1. **本地阶段**：定向检查通过后按根规则本地提交，交付可审查结果。之前对另一功能或镜像实验的授权，不自动延伸到本轮推送或生产部署。
2. **获准远端交付**：遵守现有 Draft/Ready 流程和 `merge-gate`。完整校验对应当前 head/base；改动或 base 更新后重新判断既有证据是否仍有效。开发中不要用完整 CI 代替廉价本地诊断。
3. **发布准备**：明确待发布源码 SHA、实际构建 SHA（PR merge SHA 可能不同）、镜像 ID/digest、架构、完整门禁结果及 G1。摘要中的 `release_sha` 不能被误报为 PR head。标签可变，不能只凭 tag 名字或旧绿灯判断镜像相同。
4. **部署执行**：另有明确授权后，使用 [release_manifest.py](../../scripts/deploy/release_manifest.py)、[deploy.sh](../../scripts/deploy/deploy.sh)、静态资源导出和备份／恢复入口。部署经过验证的确切镜像，不在目标环境隐式 `compose up --build` 或重新解析依赖。若必须重建，即视为新镜像，重新验证身份和适用门禁。
5. **数据与回滚**：同 SHA 静态资源、非 root、备份恢复、活跃卷保护和当前已接受的项目/端口/环境保持不变。代码 revert、切换镜像和数据库迁移回滚是不同动作；不以删除卷来“恢复干净环境”。RSS/Miniflux 独立镜像仍遵循自己的发布合同。

推送／合并／部署均须如实报告 actual 状态。临时 synthetic build 有改动时必须标注 dirty/synthetic，不能只凭真实 SHA label 将其当成干净发布镜像。

当前 release manifest 保存镜像引用，并校验 revision、非 root、迁移和静态元数据；它没有自动把所有 SHA tag 转换成内容 digest，也没有提供镜像签名验真。因此操作记录仍须保存并核对实际 image ID/digest，优先使用受支持的 digest 引用。不要把这项人工发布约束写成已经实现了新的供应链自动门禁。

## 7. 维护责任与约束边界

- 改构建输入者同时维护已有构建契约测试；改路由者同步既有路由／workflow／发布契约；改规范者执行 Agent 结构与链接检查。不要只改文档而让代码继续违反规则。
- 根 AGENTS 保留导航和全局不变量（6 KiB）；模块规则只保留入口与本领域约束（4 KiB）；细节留在本合同和现有运行指南。不要提高预算来塞入重复历史。
- 历史计划、审计文档和验收报告标明基线，不当作当前状态。持续规范不记录当前 passed 总数或“永远小于 N 秒”；这些属于逐次报告。
- 仓库根 `.worktrees/` 是已约定的本地隔离输出，不作为主项目 Agent 规则发现范围；每个 worktree 必须从自己的根独立校验。未知业务目录中的新增 AGENTS 仍须注册。
- 已有自动门禁覆盖 digest、层顺序、发布 SHA、明确 ignore 项、失败/取消传播、分流和发布身份；性能/网络/备份可用性仍需相应实际验收。本合同不意味着已经实现生产全依赖 lock、镜像签名或新的性能报警平台。
