# BYOK 单张 Codex 任务执行约束

**不要把 [T00–T14 总表](README.md) 作为一次 Codex 实现指令。**

每轮处理一个可验收功能（T00 是真实 LiteLLM Proxy + SDK + 受控上游的本地技术探针）；先核对真实 `origin/feat/byok-user-api-keys` HEAD、实际 AGENTS 和工作树。从最新功能分支切自己的 `task/byok-Txx-<short>`，PR base 指向 `feat/byok-user-api-keys`，不从旧设计基线强制重置。

1. **研发前**：对照现有代码，只提出未实现的增量；先检查成熟实现/旧任务租约/SSE/Query；记录需要保持的原有功能。
2. **技术风险**：用最小真实调用/失败注入证明最危险假设；不能依赖模型自述或作者测试摘要作为独立证据。
3. **编码边界**：完成用户一条操作链及失败路径。不得无请求改 ChatGPT 订阅登录、增加并行任务架构或独立数据库。
4. **测试规则**：同环境先跑旧基线。旧绿→新红且需求未变修代码，不准改旧断言；新旧都红查已存在缺陷/环境；产品需求改变须写明对应契约差异。
5. **防重复付费**：只读 GET/恢复没有创建/dispatch/SDK 权限；未知请求结果不自动重试。必须区分模型配置版本、credential_epoch、任务提交 token。
6. **隐私和安全**：Key 仅安全托管后端，不出现在浏览器持久层、日志、PR；翻译结果默认用户私有，推理来源为当前本人有权限的模型配置。
7. **交付证据**：更新测试文档的命令、环境、实际结果、精确 SHA、测试断言 diff、可复现用户动作和未验证项；出现大问题停在当前卡纠偏。
8. **合并**：一任务一 PR，审查通过后按实际授权合并目标功能分支，不擅自合并 main、不一次执行后续所有任务。

任务依赖满足并且已获得连续推进权限时才进入下一卡；否则交付可审核结果而非声称整个 BYOK 完成。
