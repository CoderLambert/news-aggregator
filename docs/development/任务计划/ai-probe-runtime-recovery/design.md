# AI 模型探针与本地侧车网络恢复设计

## 意图

当本地前端预览重建 `app` 容器时，与它共享网络命名空间的侧车必须一起重建；当主动模型探针返回未知或无效结果时，用户必须看到安全、可理解的具体原因，而不是误解为“已通过”。

## 目标与非目标

- 恢复当前本地 `ai-gateway`、`translation-redis` 和 `channel-worker` 与新 `app` 的共享网络。
- 修复 `local-frontend-preview.sh`，从 Compose 合并配置中识别所有 `network_mode: service:app` 侧车，并在激活与回滚时与 `app` 一起强制重建。
- 模型探针成功、明确不支持、结果未知、响应不完整等结果使用不同的中文提示；未知不使用成功色。
- 不自动重发任何可能计费的探针，不读取或更改已保存凭据，不更改数据卷。
- 不在本次修复中重构 Compose 侧车架构或 LiteLLM 数据库。

## 选定方案

采用“运行环境恢复 + 预览脚本防复发 + 页面反馈可读化”。仅恢复容器会在下次前端预览时复发；将网关改为独立网络服务则会扩大安全和部署改动。

## 验收边界

- 脚本合成测试证明能识别共享 `app` 网络的侧车，并在激活、回滚命令中带上它们。
- 前端组件测试证明 `succeeded`、`unsupported`、`result_unknown` 和 `incomplete_or_invalid` 的用户反馈，且不会自动重试。
- 当前 Compose 项目中目标服务全部恢复健康，`ai-gateway` 可访问其数据库；不运行真实供应商探针。
