# CI 持久缓存生命周期实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让 NewsHub 依赖缓存可诊断、可预热、可续装并可安全回收，同时补齐 Docker 构建失败后的下载复用。

**Architecture:** 安装器拥有 key、健康检查和 checkout 链接行为；maintenance profile 只负责在正确镜像、UID 和卷中调用安装器。独立维护程序负责 keyed 目录的只读状态和受锁定回收，`manage.sh` 负责 Runner 上线顺序。

**Tech Stack:** Bash, Python 3.12 standard library, Docker Compose v2, Dockerfile BuildKit, unittest.

**Spec:** `docs/development/任务计划/ci-persistent-cache-lifecycle/完整方案.md`

## 全局约束

- 只使用合成临时目录和只读 Compose 配置进行开发验证，不触碰真实 Runner 缓存卷。
- Python 3.12、Node 22、依赖版本、lock 文件和 CI 路由保持不变。
- 缓存删除默认 dry-run，执行路径只允许 64 位十六进制 keyed 目录并持有安装锁。
- 每个行为先写能捕获缺失能力的失败测试，再实现最小改动。

## 评审重点

- 显式 `PIP_CACHE_DIR` / `npm_config_cache` 是否真正优先，缺省路径是否仍在持久缓存根内。
- `--status` 是否完全无安装和无 checkout 写入副作用。
- 新 checkout 是否能共享 HIT，失败安装是否跨进程继续 RESUME。
- maintenance 服务是否隔离前后端卷，预热失败时 listener 是否保持离线。
- GC 是否可能跟随符号链接、删除当前 key、下载缓存、锁或未知目录。
