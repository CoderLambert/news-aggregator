# CI 持久缓存生命周期完整方案

## 意图

Runner 新建持久卷或依赖安装中断时，先在本地维护阶段完成可续装的缓存预热，再允许 GitHub Runner 领取任务。正常源码重试必须命中已有环境；锁文件变化只产生一次明确的冷安装。

## 已有能力

- 后端环境按 Python ABI、架构、依赖文件和固定大包版本寻址；`a368128` 已实现中断后 `RESUME`、持久 pip 下载缓存和原子完成标记。
- 前端按 Node/npm/平台与 package lock 寻址，完整命中时跳过 `npm ci`。
- Runner 工作卷、前端工作卷和 DinD 数据卷均由 `newshub-ci` Compose 项目持久保存。

## 选定方案

采用“安装器自描述 + 隔离维护容器 + 上线前预热 + 定向回收”：

1. 后端、前端安装器统一支持状态查询和只写缓存、不修改 checkout 的维护模式；显式环境变量优先，缺省值仍落在内容寻址缓存根下。
2. Compose 增加两个 maintenance profile 服务，分别只挂后端或前端持久卷，并只读挂载源码。`manage.sh` 在首次安装、启动和更新 Runner listener 前运行预热。
3. 新的缓存维护程序只识别 64 位十六进制 keyed 目录，默认 dry-run；执行时持有与安装器相同的锁，保留当前 key 和最近成功条目，不调用任何全局 prune。
4. Dockerfile 为 RSS pip、前端 npm 和 Torch pip 增加独立 BuildKit 下载缓存；镜像层契约和依赖版本不变。

## 约束与非目标

- 不读取或修改凭据、业务数据库、生产卷或真实 provider。
- 不自动删除当前缓存，不调用 `docker system prune`、`docker volume prune` 或 Compose `down --volumes`。
- 不改变依赖版本、lock 文件、Runner 身份、CI 路由或测试范围。
- 本阶段仅做合成测试、脚本语法和 Compose 配置验证；真实 Runner 预热、Docker 构建、G1 和远端 CI 等待用户本地验收后再执行。

## 安全假设

- **SOURCE_ONLY**：maintenance 服务使用与 Runner 相同的镜像、UID/GID 和对应工作卷，因此可复用同一缓存权限；合成 Compose 测试后仍需真实空闲 Runner 验收。
- **SOURCE_ONLY**：Dockerfile 已声明 BuildKit v1 语法，支持 cache mount；真实失败续传效果在镜像构建前为 `NOT_RUN`。
- **PROVEN（已有）**：后端同 key 的中断安装能 `RESUME`，完成后再次运行能 `HIT`。

## 验收条件

- 新 checkout 共用同一缓存根时，完成环境为 `HIT`；中断环境为 `PARTIAL` 并能 `RESUME`。
- 前端和后端都明确报告 `STATUS`、短 key 和 cache root；状态查询不安装依赖、不创建 checkout 链接。
- maintenance profile 的两个服务不交叉挂载缓存卷；预热先于 listener 上线。
- 定向回收默认只列计划，执行模式保留当前 key、最近成功 key、下载缓存和锁文件。
- Dockerfile 三个易中断下载步骤均使用独立持久 BuildKit cache mount。
