# RSS渠道搜索与订阅最小MVP方案

## 要验证的事情

用户能从已经导入的RSS渠道中找到自己想看的渠道，并成功订阅。

## 功能范围

1. 接入用户已选的[tidings-top200.opml](tasks/catalog/tidings-top200.opml)，不再选源或补数。
2. 在现有“添加订阅”入口展示、搜索这些渠道；输入名称或RSS地址，使用现有普通文本匹配，提供基本“加载更多”。
3. 选中渠道并确认订阅，复用现有订阅服务和连接记录，保留当前个人分类/分组确认能力。

## 实现方式

- 数据：复用directory.py的v1快照模型和导入接口，把这份OPML适配成现有目录格式；同步更新内置种子及checksum，避免后台重新导入旧清单。
- 搜索：复用现有q搜索和cursor，不另做语言分类、同义词、相关度评分或搜索引擎。
- 订阅：复用DiscoverDialog和现有POST /api/me/rss-subscriptions/，沿用后台Miniflux连接及添加记录。
- 保留现有权限、CSRF、幂等和地址安全限制，不为快速开发绕过它们。

本次不做独立发现页、推荐系统、健康核验平台、公共频道投影、目录v2、新模型迁移、性能基准或自动化测试体系。网站发现等已有功能原样复用，不扩展成新的开发任务。

## 输入已确定

本地文件200个不同Feed地址、14个原始分类，SHA-256为 `642a56712e128fa37c8239845d33ea7c8c216b69cf9f9087924a6db208db9e04`。保留原名单，缺失字段不抓取补齐；6个HTTP地址按现有策略记录受限原因，不擅自升级或补其他来源。导入目录不等于自动订阅全部200个。

## 开发与验收顺序

按[三个任务](任务执行计划.md)依次开发。每完成一个功能，提供可运行版本/入口、改动说明、3～4步用户验收及已知限制，由用户实际测试，发现问题再修。

本轮不要求先写失败测试，不安排全量回归、压力或浏览器自动化；自动化测试在功能验证后按实际需要补。开发者只做交付所必需的构建/启动可用性检查，不把“未测”说成“通过”。

完成标准就是：能看到导入渠道、能搜索找到、能订阅并在我的频道/添加记录看到结果。连接成功与文章首次同步分别说明，不承诺提交后立刻出现文章。
