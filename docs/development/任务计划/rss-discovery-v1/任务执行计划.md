# RSS搜索与订阅MVP：三个开发任务

**目标：** 让用户从已导入的RSS渠道中搜索并订阅，快速验证这条流程是否好用。

**实现原则：** 复用现有目录、搜索、添加弹窗、订阅接口和Miniflux，按功能最小修改；渠道就是渠道，不增加语言专项设计。

**当前范围：** 最小功能已接入本地验收环境，等待用户测试。每完成一项，交付运行入口、简短改动说明和本卡人工验收步骤，由用户实测反馈；自动化测试后补。

## 三个任务与顺序

| 顺序 / 保留编号 | 做什么 | 用户验收重点 | 状态 |
|---|---|---|---|
| 1 / [RSSD-01](tasks/catalog/RSSD-01-接入已选定的TidingsTop200清单.md) | 接入已选Top200 | 看得到导入清单，地址正确，未自动订阅全部 | 已接入 / 待用户验收 |
| 2 / [RSSD-03](tasks/discovery/RSSD-03-搜索已导入渠道.md) | 搜索已有渠道 | 按名称/地址找到、空结果清楚、可以加载更多 | 已接入 / 待用户验收 |
| 3 / [RSSD-07](tasks/subscriptions/RSSD-07-订阅搜索结果.md) | 订阅搜索结果 | 确认后能看到自己的订阅/连接结果，状态真实 | 已接入 / 待用户验收 |

依赖顺序：RSSD-01 → RSSD-03 → RSSD-07。原编号保留，其他旧任务及子编号退出本次MVP，不另做前置工程。

## 交付方式

每次只汇报：做了什么、打开哪里、按哪几步操作、应该看到什么、已知问题。用户回复PASS/FAIL/未测；发现问题再按实际反馈修复。不得把构建成功、任务保存或未测说成用户验收通过。

自动化测试、完整CI回归、压力测试、真实来源批量核验等后补；本轮不要求测试先行、不扩充测试体系。开发交付保留必要构建/启动可用性检查和现有权限/安全限制。

目录v2、新模型/迁移、推荐/健康体系、公共频道投影、独立发现页、特殊搜索算法均不属于MVP。仅维护[最小方案](完整方案.md)及这三张卡；旧大方案留在archive，不是当前执行要求。

## 输入与运行边界

来源就是用户提供的[Top200 OPML](tasks/catalog/tidings-top200.opml)，不补源、不替换。导入失败保留旧目录；现有受限地址显示真实原因。保留已有订阅、文章、账号和数据库，不执行清空。代码提交、合并及部署仍按实际授权分别进行。
