# 向量检索部署前检测与配置推荐

## 目标与范围

用户在部署前通过一个入口看到机器能力、可用部署方案和模型建议，能理解推荐原因，再选择执行。普通用户不需要填写 PyTorch/CUDA 版本、向量维度、显存阈值、模型路径或 Compose 文件组合。

流程为：只读检测 → 推荐报告 → 用户选择配置 → 现有部署流程。报告不构成执行授权。沿用现有不可变镜像、显式项目/环境文件、备份、迁移、健康检查和静态资源切换，不另造发布系统。

设计目标首期支持 Linux 的 CPU 与 NVIDIA CUDA；其他 GPU 平台明确标记未支持 GPU 自动推荐，保留 CPU 方案，不把未验证的后端当作可用。当前已验证的是现有应用使用的本地 CUDA 镜像衍生版本和 MiniLM CUDA 编码；GPU 实现仍在独立分支，尚无进入主线的通用 GPU 镜像发布。全文分段索引、重排序和检索质量优化是后续独立范围，不混入机器检测功能。

## 用户入口与配置

建议增加专用入口 `./scripts/deploy/recommend.sh`（尚未实现）。现有 `preflight.sh` 用于固定站点的 DNS/TLS/SSH 部署前检查，不承担硬件探测；新入口可复用适用的只读部署辅助逻辑。本设计中的硬件探测与推荐尚未实现，默认仅输出人可读报告，可选输出 JSON 供部署工具读取。探测无需先准备应用密钥或读取真实环境文件。

普通用户保持“自动推荐”即可，不需要先选择模型。自动推荐是选择策略，实际配置分为三档：

| 档位 | 模型与定位 | 首期默认行为 |
| --- | --- | --- |
| 轻量 | 现有多语言 MiniLM；低占用、CPU 友好 | 无可用 CUDA 或新部署资源不足时推荐；GPU 轻量运行仍可手选 |
| 均衡 | **Qwen3-Embedding-0.6B**；提升中英文检索能力 | **具备合适 CUDA 资源时的默认升级目标**，先报告、验证、再按用户选择部署 |
| 精度优先 | Qwen3-Embedding-4B；更高公开检索成绩 | 高级可选候选；需单独验证显存、并发和延迟，不自动采用 |

首期默认走“自动推荐 → 资源合适则均衡 0.6B，否则推荐轻量方案”，不让用户承担 PyTorch/CUDA、向量维度或阈值配置。资源不足只影响新部署的推荐，不能静默改变已有模型/索引组合。4B 入口可在后续实测通过后开放，当前不宣称已支持；8B 不纳入第一版部署方案。

高级选项才暴露强制 CPU/GPU、模型档位、批量上限和离线模型位置。用户明确选择精度优先时，才评估 4B。第一版不默认加载重排序模型，不把额外显存和请求延迟作为基础部署成本。

报告展示：检测结果、推荐档位、模型与运行设备、推荐镜像/部署方式、选择理由、资源估算及其置信度、前置问题、后续命令和回退方式。示例中的执行命令需带真实解析出的固定版本，不能默认 latest。

## 探测边界

- CPU 架构、核心数、内存总量/可用量、目标存储可用空间。
- Docker/Compose 是否存在、当前用户能否访问目标 Docker、平台架构是否有对应镜像。
- NVIDIA 型号、驱动、总显存和当前可用显存；宿主信息与容器能力分别报告。
- CDI/Container Toolkit 是否就绪。只有宿主 nvidia-smi 成功，不足以判定容器 CUDA 可用。
- 检查已有目标镜像/公开模型缓存及其版本；不遍历凭据、历史文章或其他应用活动。
- 默认不拉取镜像、不下载权重。若已有合适镜像，可在有界临时容器中验证 CUDA，容器无站点环境文件/密钥/数据库挂载，结束只清理自身资源。
- 现有资源不足或无法探测时记录 UNKNOWN/受限，不凭 GPU 型号宣称运行成功。严格的只读检测不自动启动训练、索引、模型加载或基准测试。
- 需要精确判断均衡/精度优先档时，单独提供显式的试运行操作：先展示所需下载、临时资源和执行内容，再按用户选择执行。有界试运行记录实际峰值显存和编码延迟；估计值与实测值分开。

## 推荐规则

目标是让基础镜像分别提供 CPU 与 CUDA 变体；部署前选择依赖/镜像，运行时选择计算设备，不在业务请求中重装 PyTorch。当前 CUDA 支持仍在独立分支，本机验证通过的本地镜像衍生版本不等于已发布的通用镜像。GPU 缺驱动或容器接入能力时列出修复步骤，CPU 部署仍是独立可选方案；不静默安装系统包、改 Docker daemon 或重启共享服务。

轻量档沿用现有多语言 MiniLM。均衡档明确选用 Qwen3-Embedding-0.6B、1024 维、受控输入长度与经硬件验证的 FP16/BF16，作为默认升级目标；查询侧按模型要求使用检索指令，文档侧不追加查询指令。精度优先档候选为 Qwen3-Embedding-4B，不能与 0.6B 共用索引。选型已确认不代表运行已切换，资源通过也不代表 NewsHub 检索精度已验收。CPU/GPU、dtype、批量和并发上限纳入同一配置计划，保留必要安全余量，不能只凭显存总容量分档。

自动推荐考虑可用内存/显存、其他进程占用、模型权重及运行时估算、web/indexer 多进程模型副本和并发。明确按主机资源预算两类进程，不允许每个进程独立把全部显存视为可用。模型下载受网络影响时提供离线缓存方案；无缓存不假装就绪。

对于已有安装，报告先读取经过授权的非敏感有效配置。已经启用的模型保持固定；检测出更强硬件时仅建议升级，不因启动时可用显存变化反复切换模型。硬件快照带时间戳，执行前重新验证，报告不保证未来资源可用。

## 公开测评与选型依据

以下是 2025 年公开测评的固定结果，不代表最新排名或 NewsHub 实测：

| 模型 | 多语言检索 | 中文检索 |
| --- | --- | --- |
| BGE-M3 | 54.60 | 此表未提供 |
| Qwen3-Embedding-0.6B | 64.64 | 71.03 |
| Qwen3-Embedding-4B | 69.60 | 77.03 |
| Qwen3-Embedding-8B | 70.88 | 78.21 |

来源：[Qwen 模型卡评测表](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B#evaluation)。这是模型发布方提供/汇总的数据。4B 相比 0.6B 中文高 6.00 分；8B 相比 4B 再高 1.18 分。分数不是搜索正确率百分比；0.6B 作为当前均衡起点，不能宣称质量等同 4B。

[FinMTEB 论文表 10](https://aclanthology.org/2025.emnlp-main.179.pdf#page=18)的独立中文金融检索测评中，当前完整型号 paraphrase-multilingual-MiniLM-L12-v2 为 0.3795，BGE-M3 为 0.6243，指标 NDCG@10。这些领域分数不能与通用测评分数拼接或推算 Qwen 相对当前模型的精确提升。

[Qwen 重排序实验](https://qwenlm.github.io/blog/qwen3-embedding/)在 Qwen0.6B 召回 top-100 上，加 Qwen0.6B Reranker 后，多语言检索由 64.64 到 66.36，中文由 71.02 到 71.31。该中文增益仅 0.29 分，不支持默认增加小型 Reranker 就一定显著改善中文检索的结论。重排序按后续实际需要单独评估。

实际升级验收仍需比较 NewsHub 查询上的相关性、跨语言召回、延迟与资源占用。GPU 相对 CPU 的 MiniLM 编码加速结果不能套用于 Qwen0.6B 或 4B。

## 模型与索引一致性

应用和索引 Worker 使用同一份持久化有效模型配置。模型标识、固定权重 revision、向量维度、查询提示版本、文档编码/截断策略、归一化与索引版本组成一致性契约；不能仅替换 MODEL_NAME 或单独让每个进程自动选型。

CPU/GPU 设备回退使用同一模型与编码契约。运行中 GPU OOM 时只做有界批量缩小/重试；只有该模型在 CPU 内存预算内时才可回退，保留错误与实际设备信息。不能为恢复服务临时换成 MiniLM 查询 Qwen 索引。

用户选择升级后，新模型建立独立候选索引，验证完成再通过现有受控切换机制激活。构建期间继续使用旧模型/旧索引组合；失败保留旧组合。不得混写维度或模型不同的向量，不清空旧索引。升级覆盖的索引任务仍遵守单写者锁、取消、版本和所有权围栏。

订阅、分组和账号可见范围在关键词、语义、混合和回退路径保持一致，未知授权关闭访问。报告或配置升级不自动打开原本关闭的语义索引，不自动触发全站重建。

## 现有代码接入点与风险

- `Dockerfile`、GPU 独立分支中的镜像配置：镜像选择与依赖；合并前核对既有 GPU 分支。
- `scripts/deploy/` 与 release manifest：新增只读前置报告，执行仍复用原部署闸门。
- `embedding.py`：设备、模型加载、维度和编码策略，目前固定 MiniLM、空输入返回 384 维。
- `search_index.py` / `search_index_control.py` / `VectorStoreService`：复用候选集合与模型版本判断；当前模块级 MODEL_NAME 和默认参数绑定不能充当跨进程动态配置。
- 持久化配置字段及迁移的最小增量在实施计划中确定，保持现有数据；不在设计阶段修改数据库。

关键待验证假设：现有候选索引切换能扩展为模型和索引整体切换（SOURCE_ONLY，跨进程加载/并发验收尚未完成）；均衡/精度优先档能在目标并发预算内运行（UNPROVEN，当前只验证 MiniLM CUDA，未实测 Qwen）。

## 本机检测示例：2026-10-22 会话

本轮只读探测得到：i7-12700K、20 逻辑线程、约 62.5 GiB RAM，其中当时可用 25.5 GiB；目标磁盘剩余约 441 GiB；RTX 5060 Ti，总显存约 15.9 GiB，当时可用约 13.2 GiB；Docker 29.7.2。现有应用容器使用本地 CUDA 镜像衍生版本，PyTorch 2.14.1+cu130，CUDA available 为 true；这不证明主线已有可移植的 GPU 镜像发布。

推荐：轻量 GPU 为已验证方案；默认升级目标为均衡 GPU/Qwen0.6B，需通过试运行后采用；4B 仅保留高级候选。前序已确认标准 NVIDIA CDI 未配置，当前应用采用显式设备/驱动库映射，因此新机器的标准 GPU 部署不能直接标为前提齐备。动态可用资源与支持状态须在正式执行前刷新。

## 验收与交付边界

- 纯检测运行前后不改变依赖、环境文件、服务状态、模型缓存、数据库或索引；探测有超时，错误不会泄露凭据。
- 覆盖无 GPU、CPU-only Torch、GPU 宿主可用但容器不可用、低显存、其他进程占用、离线/缺缓存、多进程预算和未知平台。
- 用户能在报告中明确区分可直接部署、需要补齐前提、需要试运行与不支持。
- 同模型 CPU/GPU 一致性、均衡/精度优先档峰值资源/延迟、模型更换时新旧索引配对、取消/失败回退、权限范围分别验收。
- 本阶段只交付设计和本机只读示例，不交付探测 CLI 或自动升级实现；后续制定实施计划时以本轮默认 0.6B 的选型为准。
