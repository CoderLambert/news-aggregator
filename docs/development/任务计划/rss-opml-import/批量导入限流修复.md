# OPML 导入的临时限流改为排队等待

用户在导入列表中看到大量 `处理失败 · throttled`。本次从本地 main `3e955a6838e0ae517f6174775f0f431c6a634632` 开始修复。用户要求不运行检测，并优先合入本地 main；本轮不运行测试、构建、CI 或负载测试，不推送远端。

## 原因与改动

SOURCE_ONLY：`process_imports → subscribe → check_addition_limit` 复用了逐条新增配额，默认每账号每小时 20 个目标、同时 5 个活动连接任务。`process_imports` 把 Throttled 作为一般失败持久化。这是本地的准入/失败分类问题，不能据此判断对应 RSS 站点失效，也不能说明全站只允许 5 个用户。

- 已确认的 OPML 使用服务内部的 bulk_import 参数，不按每小时 20 条手动新增配额逐项拒绝。HTTP 订阅请求仍使用原限制，客户端不能提交该参数。单文件 500 项/1 MiB、账号订阅总量、URL 安全和后台 worker 并发限制保留。
- 批量导入的活动目标仍最多 5 个（或现有配置值），只统计 pending/running/retry_wait。unknown/manual_blocked 的目标继续保留原有逐 binding 核对/fencing，不因它们阻塞其他无关 Feed。没有扩大真实 worker 并发，也没有重发这些未知结果。
- 活动连接名额满时保留 pending，按 Throttled.wait 设置批次冷却；等待期间不反复调用 subscribe、不创建额外操作、不将整个剩余批次标失败。JSON 批次 options 保存持久冷却时间，无新增迁移。
- 已有失败记录只自动恢复满足以下条件的项：本地 throttled、operation 为空、已确认、未移除、账号有效、批次处于 confirmed/complete。恢复每轮最多 limit 项。由于 subscribe 的 savepoint 已回滚且未产生操作，此类恢复不重发未知远端请求；其他失败和已有 operation 的记录保持原处理。
- 达到账号订阅总量时返回明确的 subscription_limit，不作为暂时名额不足循环恢复。
- 进度接口把可恢复旧限流项显示为等待，前端显示中文冷却提示；成功提交连接后清掉旧限流提示。
