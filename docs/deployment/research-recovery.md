# Research run recovery

Research requests now use durable, owner-scoped runs and ordered event records rather than an in-process daemon-thread registry. The design follows ADR-028 and `contracts/RESEARCH-RECOVERY.md`; the database is authoritative, while process-local notifications are only a wake-up optimization.

## Request and recovery lifecycle

`POST /api/research/` creates a session and run; `POST /api/research/<session_id>/chat/` starts a follow-up run. Both accept `Idempotency-Key` (1–64 printable ASCII characters; omitted keys are generated by the server) and return an event stream with `Session-ID` (create), `Run-ID`, and `Run-Status` headers. Repeating the same key and request attaches to the same run. Reusing a key with a different request returns `409 idempotency_key_reused`; another active run in the same session returns `409 research_run_active`.

Runs move through `queued`, `running`, and one terminal state: `succeeded`, `failed`, `cancelled`, or `interrupted`. An active run has a 60-second lease renewed every 20 seconds. A stale running lease becomes `interrupted`; started provider/tool work is not automatically replayed. A queued run can be explicitly re-dispatched only by resubmitting the same idempotency key. A failed, interrupted, or cancelled request is not retried implicitly; a new user action uses a new key.

`GET /api/research/<session_id>/stream/` is owner-only and read-only: it replays persisted events for an active run or returns the saved session and safe latest-run state. `POST /api/research/<session_id>/cancel/` accepts `{ "run_id": "..." }` and fences only that exact latest run. Repeated cancellation of a terminal run is idempotent; a changed run ID returns `409 research_run_changed`. Session deletion fences active workers before the existing cascade removes runs and events. Session authentication and CSRF protection apply to unsafe requests; owner DTOs and streams are `Cache-Control: no-store` and streams disable proxy buffering.

The browser stores recovery pointers in `sessionStorage`, namespaced by viewer and session. Reconnecting replays the same run; it does not submit a new request. Explicit Cancel calls the server cancellation endpoint. Closing the panel, changing sessions, unmounting, or losing the network only aborts the browser's SSE connection; it does not cancel the worker. A new research attempt is an explicit user action and receives a new idempotency key.

## Execution and resource bounds

Research runs share the existing two-worker translation executor; there is no additional executor or general-purpose queue. At most two runs are admitted per application process, including submitted work waiting for a worker. A full run capacity returns `503 research_capacity_reached` with `Retry-After: 1`. SQLite writes use conditional run-token/status/lease checks before persisting events, tool results, or final session history. Final messages and `succeeded` state commit atomically; stale workers cannot overwrite cancellation or a newer run.

SSE request threads are separately limited to two per process for the AI chat, translation, research create/chat, and research stream routes. Admission occurs before view side effects; saturation returns `503 sse_capacity_reached` with `Retry-After: 1`. Disconnect releases only the SSE slot. This is an application resource bound, not a per-user usage or token quota.

Each complete UTF-8 event record is limited to 16 KiB and each run to 2 MiB of persisted event bytes. Text deltas are split at Unicode boundaries into pieces no larger than 2048 UTF-8 bytes. The frontend parser bounds its pending SSE buffer at 32 KiB. Full successful answers remain available in the owner-scoped session; event limits do not truncate saved conversation history.

## Provider and hosted-site boundary

When `PUBLIC_AI_ENABLED=0`, the existing public policy rejects AI requests before the view. Production remains fail-closed even if that feature switch is explicitly enabled: research session/run writes and provider/tool network calls are rejected with `503 hosted_integration_unapproved`. Development keeps the configured provider behavior. No real OAuth, model/provider request, hosted deployment, or production approval is part of this change.

The migration `0031_research_run_recovery` creates only the research run/event tables and depends on translation migration `0030_subscription_translation_task`. It does not rewrite or migrate existing research sessions or search results.
